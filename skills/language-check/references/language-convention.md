# 語言分界慣例

適用範圍：採用此 skill 的 repo。這份文件說明 `SKILL.md` 裡那條規則「為什麼」長這樣，
以及在判斷會卡住的邊界情況上該怎麼決定。規則本身在 `../SKILL.md`，這裡只談理由。

---

## 1. 判準是「誰讀」，不是「哪種檔案」

只有一個問題決定一段文字用什麼語言寫：**這段文字最終是誰在讀？**

一般人的直覺是照檔案類型分 —— 「文件用中文，程式碼用英文」。這個直覺會在第一個邊界案例
就失效，因為它答不出「錯誤訊息算哪一種」。錯誤訊息是寫在程式碼裡的字串，但它是要給人看的；
按檔案類型分類，它兩邊都站得住腳，於是每個人各憑感覺，同一個 repo 裡就會同時出現中文和
英文的 error message。

改以讀者為判準，這個問題就有唯一答案：錯誤訊息會被印進 log、CI 輸出、issue 的貼文裡，
讀它的人不一定是寫它的人，那份輸出也不保證留在這個 repo 裡。所以是英文。

### 1.1 繁體中文那一側

只有「確定只會被這個 repo 的人類維護者讀到」的文字才用繁中：

| 內容 | 為什麼是中文 |
|---|---|
| 程式碼註解、docstring | 註解不會被執行、不會被輸出、不會離開原始碼。它唯一的讀者就是打開這個檔案的人。用母語寫，能塞進去的推理密度遠高於用外語寫 —— 而註解的價值幾乎全部來自那些推理。 |
| `README.md` | 給要用這個 repo 的人看的。 |
| `references/` 下的設計與理由文件 | 給要改這個 repo 的人看的。像這份文件本身。 |

註解這一項值得多講一句。註解要記錄的是「為什麼是 A 不是 B」、「這裡看起來可以簡化但不行，
因為……」這類東西。用不熟練的外語寫，作者會不自覺地把它縮短成一句沒有資訊量的複述
（`# 取出 command`），而用母語寫才寫得出真正有用的那三行。這條規則的實際效果是**提高註解
的品質**，不只是換個語言。

### 1.2 英文那一側

| 內容 | 為什麼是英文 |
|---|---|
| **所有 runtime 輸出** —— stdout、stderr、丟出的例外、UI 上的字 | 見下方 2. |
| 機器讀的檔案：`SKILL.md`、`CLAUDE.md`、`AGENTS.md`、各種 manifest、hook 設定 | 這些是給模型或工具鏈解析的輸入，不是給人讀的散文。 |
| hook 注入模型 context 的字串 | 同上 —— 它的讀者是 Claude。 |
| 會散佈出去的東西：套件 metadata、commit message | 一旦 push 出去，讀者就不再限於這個團隊。 |
| 識別字：函式與變數名、CLI 參數、設定 key、檔案路徑 | 沒有討論空間。 |

## 2. 為什麼 runtime 輸出一定是英文

這是整條規則裡唯一會被反覆質疑的一項 —— 「錯誤訊息給人看，為什麼不能用中文？」有四個理由，
任何一個單獨都不夠強，合起來才成立：

1. **輸出會離開這個 repo。** 訊息會被貼進 issue、丟進 CI log、轉給沒有這份原始碼的人。
   註解不會發生這種事，輸出會。
2. **輸出會被 grep 和被比對。** 這個 repo 的測試套件就直接靠 stderr 的字串比對來確認
   「觸發的是對的那個錯誤」（見 `../../commit/tests/test-commit-msg-hook.sh` 的
   `stderr_pattern` 參數）。中文字串在跨平台的 grep、編碼、terminal 上都多一層變數。
3. **編碼會壞在最不該壞的時候。** 一段中文的 error message，在 Windows 的 cmd.exe、
   非 UTF-8 的 CI runner、或被重導向到檔案再被別的工具讀進去時，可能變成一堆亂碼。
   它偏偏只在「出事的時候」才被印出來 —— 那正是你最不希望它讀不懂的時刻。

   這一條原本寫得像個假設，2026-08-18 實測之後才知道它比想像中硬，而且**不只中文會踩到**。
   Python 給 stdout 的是 `errors=surrogateescape`、給 stderr 的是 `errors=backslashreplace`，
   所以同一個編不出來的字元，在兩條串流上是兩種完全不同的失敗：

   | 字元 | cp950 | cp437 | cp1252 |
   |---|---|---|---|
   | em dash U+2014 | 可編碼 | **crash** | 可編碼 |
   | 箭號 U+2192 | 可編碼 | **crash** | **crash** |
   | 警告號 U+26A0 | **crash** | **crash** | **crash** |

   stdout 那側直接拋 `UnicodeEncodeError`、中止整個執行；stderr 那側則靜靜降級成 6 個字元的
   逃逸字面（U+26A0 會變成 `backslash-u-2-6-a-0` 這六個字），日誌看起來還在動，訊息其實已經
   壞了。**「實際上沒出事」不能當辯護** —— em dash 活過 cp950 純粹是運氣，同一個字元在 cp437
   就是當場中止。所以這條規則要求的不是「沒有中文」，是**純 ASCII**。
4. **執行期的錯誤訊息常常也是給機器讀的。** hook 的輸出、exit code 搭配的訊息、
   被上層程式解析的字串 —— 用英文才不用去想「這個字串有沒有人在 parse」。

所以判準可以濃縮成一句可以直接檢查的話：

> **`.sh` / `.py` / `.js` 的字串字面值裡不准出現任何非 ASCII 字元。**

註解裡多少中文都可以，字串裡一個都不行 —— 而且不限於中文：符號、em dash、全形標點一律不行，
理由就是上面那張表。這句話好就好在它不需要判斷「這個訊息是給誰看的」，它是一條 grep 得出來的
機械規則。

**但它是必要條件，不是充分條件。** 原始碼那一行乾淨，不代表輸出乾淨 ——
`print(f'the "{label}" column is empty')` 整行一個非 ASCII 字元都沒有，卻會在 `label` 綁到
中文顯示名時印出中文。這一類「經插值進入輸出」的違規，任何文字掃描都看不到，只能人工回溯
插值來源。見 4.3 的第三個盲點。

## 3. 看起來像矛盾、其實一致的幾個案例

這幾組每次都會被拿出來問，先寫在這裡：

### `README.md` 是中文，`CLAUDE.md` 是英文

兩個都是根目錄的說明性散文，語言卻不同。因為讀者不同：`README.md` 給人讀，`CLAUDE.md` 給
Claude 讀。判準是誰讀，不是「是不是文件」。**不要為了整齊而統一它們。**

### `SKILL.md` 是英文，同一個 skill 的 `references/*.md` 是中文

同一個目錄裡兩種語言，一樣不是疏漏。`SKILL.md` 是模型執行時讀的指令；`references/` 是人在
質疑某個設計決定時才會翻開的理由文件。這份文件本身就是例子。

### 註解裡夾英文不算違規

`# core.hooksPath 屬於共用設定，因此用 --git-common-dir（而非 --show-toplevel）才能……`
—— 中文散文裡的指令、識別字、路徑保持原樣，這是正確寫法，不是「混用」。要盯的是**輸出**
有沒有混，不是散文有沒有混。

### commit message 是英文，即使回覆是中文

commit message 是產出的成品，會被 push 出去，讀者不限於這個團隊。

### 這條規則和 `reply_zh_hant` 選項無關

最容易搞混的一組。`claude-min-plugin` 的 `reply_zh_hant` 選項管的是 **Claude 用什麼語言
「回覆」使用者**；這份文件管的是 **檔案內容用什麼語言「撰寫」**。兩者互不影響：即使關掉
`reply_zh_hant`，程式碼註解仍然是繁中；即使開著，error message 仍然是英文。
`hooks-handlers/user-prompt-submit.sh` 注入的文字第二句就是為了把這兩件事分開才存在的。

## 4. 偵測方法與它的極限

`SKILL.md` 的步驟用 grep 做偵測。這裡說明它為什麼夠用、以及在哪裡不夠用。

**用到的 Unicode 範圍**：`U+4E00–U+9FFF`（CJK 表意文字）、`U+3000–U+303F`（中日韓標點，
`「」`、`、`）、`U+FF00–U+FFEF`（全形，`／`、`：`）。

**刻意排除 `U+2014`（em dash `—`）**。這個 repo 的英文散文大量使用 em dash，把它算進 CJK
範圍會讓幾乎每一行英文都變成誤報。這是實測過才拿掉的，不是漏掉。

### 4.1 掃描範圍：為什麼是「全部非二進位檔案」

這個決定繞了兩圈才定案，兩圈都是實際跑出來才發現的，值得記下來免得有人再繞一次。

**第一版用副檔名 glob（`*.sh`、`*.py`、`*.js`、`*.ts`）挑執行檔，漏掉了最該掃的檔案。**
git hook 是沒有副檔名的腳本 —— 本 repo 的 `skills/commit/hooks/commit-msg` 就是一支 bash
腳本、沒有副檔名，而它同時是全 repo 錯誤訊息最密集的檔案（16 行 `>&2`）。glob 只匹配到 5 個
檔案，違規掃描漂亮地回報「乾淨」，卻從頭到尾沒打開過那一個。**漏掃不會報錯，只會給你一個
假的綠燈**，這比不掃還糟。

補上 shebang 掃描能救回 `commit-msg`，但救不了有副檔名、卻沒有 shebang 慣例的語言：
`.ps1`、`.bat`、`.go`、`.rs`、`.cs`、`.tsx` 兩邊都接不住。`.ps1` 對本 repo 是很近的風險 ——
`hooks/hooks.json` 的 matcher 已經是 `Bash|PowerShell`，未來多一支 PowerShell handler 完全
合理，而它會被靜靜略過。**只要選擇邏輯是一份清單，下一個新語言就一定會漏。**

**第二版改全掃，誤報卻是結構性的 —— 只要比對式仍然只看「輸出動詞」。** 當時的比對邏輯是
「同一行有 `echo` 這個字」加「同一行有中文字元」，而一份用中文討論輸出訊息慣例的文件，
每一句都同時滿足這兩個條件。上一版為了說明這件事而寫進本節的那幾行字，自己就變成了新的
誤報 —— 誤報數當場從 4 個漲到 6 個。**文件寫得越完整，掃描結果越髒。**

**定案：全掃非二進位檔案，精準度交給比對式負責。** 要求 CJK 必須落在**輸出動詞之後的
ASCII 引號字串內**，上述整類誤報就消失了：中文註解提到 `print()` 不再命中，而
`Write-Error "<message>"`、`fmt.Println("<message>")`、`raise ValueError("<message>")`
全部照抓（示範一律用 ASCII 佔位符，寫字面中文的話這幾行自己就會被掃出來）。
實測：15 個人工構造的違規案例全數命中、6 個真實誤報降到 1 個。

檔案選擇因此變成 `grep -qI .`（grep 認定為文字檔即納入），**沒有任何清單要維護**，新語言
自動涵蓋。這也符合本 repo 準則第 9 條 Fail Loudly, Not Silently：寧可多看幾個檔案，不要
安靜地漏掉一個。

**比對式裡那段 `GAP` 不是裝飾。** 動詞與開始引號之間的空隙，只允許「非引號字元」或「完整
的引號群組」。寫成 `.{0,60}` 會讓比對式跨過一個已經結束的字串、把它的**結束引號**當成開始
引號用，於是文件裡「先寫一段引號範例、後面接中文散文」的那種行就會被誤判 —— 本文件上一版
就正好踩到。反過來只允許非引號字元，又會漏掉 `printf '%s\n' "<message>"` 這種在動詞與訊息
之間夾一個格式字串參數的合法違規。三種寫法在 15 個人工案例加本 repo 上實測：交替寫法
15/15 全中且零誤報，`.{0,60}` 多一個誤報，純非引號寫法少抓一個。

**仍然無法消除的一類：文件裡刻意寫的錯誤示範。** 一段用來說明「不要這樣寫」的
`echo "<message>"`，若把佔位符換成字面中文，逐字元就是一個違規 —— 任何比對式都分不出它和
真違規的差別，因為它們一模一樣。處理方式是寫這類反例時一律用佔位符（本文件即如此），並在
回報前確認落在文件檔裡的命中是不是反例。

### 4.2 grep 不是剖析器

判斷「CJK 在不在註解裡」需要真正的剖析器。`SKILL.md` 步驟 5 的 `grep -v '^[^:]*:\d+:\s*#'`
只認得行首註解，因此下面幾種**合法**的寫法一定會留在結果裡：

- 行尾註解：`fixes_list = FIXES_RE.findall(body)  # 例如 ["a1b2c3d", "unknown"]`
- Python 的 docstring（三引號區塊）
- `//` 與 `/* */` 註解
- zh-Hant 文件散文中剛好帶引號的句子

所以步驟 5 的產出是「待人工判讀的候選清單」，不是「違規清單」。**不要把它的行數直接當成
違規數回報。** 命中即違規、不需判讀的是步驟 4。

順帶一提，收緊比對式也讓步驟 5 變乾淨了：舊寫法（單純找 CJK）在本 repo 產生 22 行候選，
改成「找 ASCII 引號字串內的 CJK」之後剩 4 行。

寫死一個「合法的中文行數」門檻沒有意義：註解愈多這個數字愈大，而註解多是好事。要盯的是
違規數是不是 0，不是中文佔比。

這一節只做到「承認 grep 不是剖析器」。真的把剖析器接上去是 4.3 的第二個盲點。

### 4.3 三個結構盲點（2026-08-18 補入）

前兩節談的是掃描「範圍」與「精準度」。2026-08-18 在另一個 repo 實跑這個 skill 時，它回報
「零違規」，而當時的 console 輸出確實有中文欄位名與非 ASCII 符號。問題不在執行者判斷失準，
而在掃描方法有三個**結構性**盲點：只查 CJK、只看單行、只看字面量。三個都在本 repo 上覆驗過。

**盲點一：只查 CJK。** 步驟 4／5／6 全部以 `[\x{4e00}-\x{9fff}]` 為軸心，所以箭號、警告號、
勾號、emoji 每一道都通過 —— 它們既不是 CJK 也不是英文字，而是接收端 console 可能編不出來的
位元組。修法是步驟 4b：同一組輸出動詞，字元類換成 `[^\x00-\x7F]`。
**本 repo 實測**：步驟 4 回報 0，步驟 4b 抓出 **5 個真違規**，全是英文輸出字串裡的 em dash；
而文件散文零誤報 —— 4.1 那段 `GAP` 交替式在字元類放寬之後照樣守得住精準度，不需要另外限縮。

**盲點二：只看單行。** 每一條比對式都要求輸出動詞與違規字元落在**同一行**。有兩種常見寫法
會讓它們不同行，而且都不是調整比對式能救的：

- **隱式字串串接**：一個 `print()` 橫跨三行，訊息主體在第 2 行 —— 那一行看起來只是個孤立的
  字串常數，附近沒有任何動詞。
- **字串內的巢狀引號**：`print(f"No commits in {rev_range or 'this branch'} - nothing")`
  裡的 `'this branch'` 提前結束了 `[^"']` 那一段，掃描根本走不到它後面的違規字元。

修法是走語法樹：`scripts/scan_output_symbols.py` 收集 `print()` 與 `raise` 底下的所有字串
常數，再逐字元檢查。**本 repo 實測**（`skills/commit/scripts/ai_attribution_stats.py`）：
逐行 grep 看到 4 個，AST 看到 **6** 個 —— 多出來的兩個，正好一個是跨行串接、一個是巢狀引號。
一種盲點兩個成因，這是「調比對式救不回來」最直接的證據。

**巢狀引號那一半在 shell 上沒有 AST 可用，而它真的會咬人。** 落實這些規則的當下，
`commit-msg:90` 就是活例：

```
echo "       Fixes-Candidates only makes sense alongside an honest 'unknown' —" >&2
```

字串中間的 `'unknown'` 結束了 `[^"']` 那一段，步驟 4 與 4b 雙雙略過它，而 shell 沒有
`scan_output_symbols.py` 這種東西可以接。**這是在寫這一節的同時、用這一節的方法找到的第八個
違規** —— 前七個是逐行掃描與 AST 抓到的，它是第八個。

補法是步驟 4c：退回「只看輸出動詞」的寬鬆形式，但把範圍限縮到**非文件檔**。4.1 說過動詞單獨
形式在全 repo 上不可用（一份討論輸出慣例的中文文件每行都命中），而排除 `.md` 正好切掉的就是
那一整類。本 repo 實測：**3 個命中，1 個真違規（就是上面那行）＋ 2 個 docstring**，
短到可以逐行讀完。這一步不追求精準，只追求涵蓋。

**盲點三：只看字面量。** 三個裡最嚴重的一個，因為它讓 skill **回報乾淨而輸出實際是髒的**。
`print(f'the "{label}" column is empty')` 這行原始碼一個非 ASCII 字元都沒有、通過每一道掃描，
執行時卻印出中文 —— 因為 `label` 綁到了報表的中文欄位名。這一類沒有工具解，連
`scan_output_symbols.py` 也抓不到（它只讀字面常數），只能對每個輸出點回溯插值來源。
所以它在 `SKILL.md` 裡被寫成規則，而不是交給腳本。

**盲點三的修法必須配一道煞車。** 插值來源要分兩種，語法一模一樣、判定卻相反：

| 插值來源 | 判定 |
|---|---|
| repo 自己在原始碼裡定義的顯示名 | 違規 —— 應另備一組 console 專用英文名 |
| 使用者資料（watchlist 條目、檔名、使用者輸入的紀錄） | 合法 —— **不得翻譯** |

把使用者資料翻成英文是 bug，不是合規：那是使用者自己取的名字，翻掉之後他反而認不出日誌在講
哪一筆。所以盲點三的規則**不能單獨落地** —— 少了這道煞車，執行者會去翻譯不該翻的東西，
比原本的問題更糟。

至於 repo 自訂顯示名那一側的正解：**不要翻譯那個常數**。它通常同時是 UI 表頭與 dict 的鍵，
翻了會連帶炸掉 UI 與查表。保留原常數，另備一組 console 用的英文名，並在 import 時比對兩者的
鍵集合、對不上就拋例外 —— 讓漂移當場失敗，而不是靜靜把中文放回輸出。

**第四件事，是修法自己帶出來的。** 上面三個盲點補完之後，本 repo 又冒出 3 處違規，而且
**前面五道掃描全數漏掉**：

| 位置 | 違規字元 | 用途 |
|---|---|---|
| `hooks-handlers/session-start.sh:18` | 10 個 em dash | `additionalContext`，注入模型 context |
| `hooks-handlers/pre-tool-use-bash.sh:47` | 1 個 | `permissionDecisionReason`，顯示在權限提示 |
| `.claude-plugin/marketplace.json:3` | 1 個 | marketplace 描述，顯示在 `/plugin` 終端機介面 |

三個都是 U+2014（cp950 可編碼、cp437 crash），三個都是 runtime 輸出。

漏掉的原因是一個**不對稱**：步驟 4 放寬成 4b（CJK → 非 ASCII）時，負責接住它漏網的那張網
（步驟 5，不看動詞）字元類沒有跟著放寬，還停在 CJK。於是「非 ASCII 但不是 CJK、而且該行沒有
輸出動詞」這個交集，掉出了每一道掃描。前三個盲點是原方法的，**這一個是補法自己開的**。

補法是步驟 5c：把步驟 5 的字元類同步放寬。本 repo 實測 11 個命中 —— 3 個真違規加 8 個繁中
docstring。

> **放寬一張網的字元類時，接住它的那張網必須一起放寬。** 否則就是在兩張網之間開一個洞，
> 洞的大小剛好等於「新增的字元類 ∩ 舊網的條件」。

順帶一提，把 `cat` 加進動詞清單救不了這一類：`cat << 'EOF'` 在一行、違規字串在好幾行之後，
那正是盲點二。動詞清單再長都到不了，只有拿掉動詞要求的那一道到得了。

### 4.4 為什麼「歸帳」比「我看過了」有用

`SKILL.md` 原本有一條「Never claim "no exceptions" without having looked」，立意對，但它
沒有可查核的機制 —— 「我看過候選了」這句話沒有辦法驗證。改成把每一行含 CJK 的行分進四個桶
（docstring／註解／模板字串／程式字串），四個數字加起來等於該檔含 CJK 的行數、未分類為 0，
再交叉檢查「程式字串」與輸出點的交集是不是空的，就變成兩個可以驗的數字。

歸帳時有一個陷阱值得記下來：**docstring 與三引號模板長得一模一樣**，只有開頭位置能分辨
（docstring 起一整行；模板是被賦值或被當引數傳遞）。把兩者混為一談，等於把整批 UI 字串藏進
「註解都是合法的」那個桶裡 —— 而那正是稽核要找的東西。
